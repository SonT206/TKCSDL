\section{Database Design Validation Objectives}\label{s:valobjectives}

The objective of database design validation is to verify that the proposed relational model provides explicit database structures for all identified functional requirements and thirty-nine business rules. Rather than assuming artificial runtime execution times or synthetic pass/fail execution results without a live production deployment, this validation focuses on the structural correctness, relational completeness, constraint enforcement, normalization, and traceability of the schema.

Specifically, the validation process evaluates:
\begin{enumerate}
    \item \textbf{Entity and Cardinality Coverage}: Ensuring that all physical and logical concepts have corresponding relations and that cardinalities accurately mirror operational reality.
    \item \textbf{Constraint Enforcement}: Identifying which rules are enforced directly by relational mechanisms (Primary Keys, Foreign Keys, Unique constraints, Check constraints, and Partial Indexes) versus rules that require trigger, transaction, or application-level logic.
    \item \textbf{Referential Integrity and Deletion Policies}: Validating the cascade, restriction, and nullification behaviors across parent-child dependencies.
    \item \textbf{History Preservation and Audit Separation}: Confirming that business state transitions and security audit logging are structurally decoupled into dedicated, non-volatile tables.
    \item \textbf{Normalization Rigor}: Demonstrating that all twenty-three relations satisfy Third Normal Form (3NF), eliminating update, insertion, and deletion anomalies.
    \item \textbf{Index-to-Query Alignment}: Verifying that indexing strategies directly correspond to anticipated operational query access patterns.
\end{enumerate}

\section{Constraint Validation}\label{s:constraintval}

Integrity constraints provide the first line of defense for data consistency. The schema translates business requirements directly into standard PostgreSQL constraints.

\subsection{Primary Key Constraints}
Every table in the system is assigned a single-column surrogate primary key generated by the database engine (\texttt{BIGINT GENERATED ALWAYS AS IDENTITY}), or a composite primary key in the case of associative bridge tables.
\begin{itemize}
    \item \textbf{Master and Operational Tables}: \texttt{system\_user(user\_id)}, \texttt{customer(customer\_id)}, \texttt{customer\_address(address\_id)}, \texttt{delivery\_order(order\_id)}, \texttt{package(package\_id)}, \texttt{landing\_station(station\_id)}, \texttt{drone(drone\_id)}, \texttt{delivery\_activity(activity\_id)}, \texttt{tracking\_record(tracking\_id)}, \texttt{delivery\_confirmation(confirmation\_id)}.
    \item \textbf{Bridge Tables}: \texttt{user\_role(user\_id, role\_id)} and \texttt{role\_permission(role\_id, permission\_id)} enforce composite primary keys, preventing duplicate role or permission assignments.
\end{itemize}
\textbf{Validation Conclusion}: Fully enforced at the database level by PostgreSQL identity sequencing and unique b-tree indexes.

\subsection{Foreign Key Constraints}
Relationships between entities are enforced through relational foreign keys.
\begin{itemize}
    \item Orders strictly reference valid customers (\texttt{delivery\_order.customer\_id $\to$ customer.customer\_id}).
    \item Activities link orders and drones (\texttt{delivery\_activity.order\_id $\to$ delivery\_order.order\_id}, \texttt{delivery\_activity.drone\_id $\to$ drone.drone\_id}).
    \item Telemetry and exceptions link to delivery activities (\texttt{tracking\_record.activity\_id $\to$ delivery\_activity.activity\_id}, \texttt{delivery\_exception.activity\_id $\to$ delivery\_activity.activity\_id}).
    \item Rescheduled delivery activities link to preceding attempts through a self-referencing foreign key (\texttt{delivery\_activity.previous\_activity\_id $\to$ delivery\_activity.activity\_id}).
\end{itemize}
\textbf{Validation Conclusion}: Fully enforced at the database level. Referencing rows pointing to non-existent parents are strictly rejected.

\subsection{Unique Constraints}
Candidate keys and one-to-one or one-to-zero/one cardinalities are enforced via database-level \texttt{UNIQUE} constraints:
\begin{itemize}
    \item \texttt{system\_user.username}, \texttt{system\_user.email}, \texttt{system\_user.phone\_number}.
    \item \texttt{customer.phone\_number}, \texttt{customer.email}.
    \item \texttt{drone.serial\_number}.
    \item \texttt{landing\_station.station\_code}.
    \item \texttt{delivery\_confirmation.order\_id} — Enforces the business rule that a delivery order can have at most one successful delivery confirmation (BR-33).
    \item \texttt{delivery\_confirmation.activity\_id} — Ensures that each delivery activity attempt has at most one confirmation record (BR-35).
    \item \texttt{delivery\_route.activity\_id} — Enforces that an activity has at most one planned route.
    \item \texttt{route\_point(route\_id, sequence\_number)} — Enforces unique ordering of waypoints within a given route.
\end{itemize}
\textbf{Validation Conclusion}: Fully enforced at the database level.

\subsection{Check Constraints}
Domain integrity is verified through declarative \texttt{CHECK} constraints:
\begin{itemize}
    \item \textbf{Physical Dimensions and Payload}: \texttt{package.weight\_kg > 0}, \texttt{package.length\_cm > 0}, \texttt{package.width\_cm > 0}, \texttt{package.height\_cm > 0}, \texttt{drone.max\_payload\_kg > 0}.
    \item \textbf{Geographic Coordinates}: \texttt{latitude BETWEEN -90 AND 90}, \texttt{longitude BETWEEN -180 AND 180} across \texttt{customer\_address}, \texttt{landing\_station}, \texttt{tracking\_record}, and \texttt{route\_point}.
    \item \textbf{Operational Domains}: \texttt{drone.battery\_level BETWEEN 0 AND 100}, \texttt{landing\_station.capacity >= 0}, \texttt{tracking\_record.altitude\_m >= 0}, \texttt{tracking\_record.speed\_kmh >= 0}.
    \item \textbf{Discrete State Enums}: Validated on \texttt{delivery\_order.order\_status}, \texttt{package.package\_status}, \texttt{drone.status}, \texttt{landing\_station.status}, \texttt{delivery\_activity.activity\_status}, and \texttt{package\_station\_event.event\_type}.
    \item \textbf{Temporal Bounds}: \texttt{delivery\_activity.started\_at <= delivery\_activity.ended\_at}, and \texttt{station\_operator\_assignment.assigned\_from < station\_operator\_assignment.assigned\_to}.
\end{itemize}
\textbf{Validation Conclusion}: Fully enforced at the database level.

\section{Advanced Relational Enforcements}\label{s:advancedenforcement}

Certain business rules represent classic challenges in relational database design that go beyond simple single-column constraints. The proposed design incorporates advanced relational modeling techniques to enforce these rules directly:

\subsection{Customer Address Ownership Validation (BR-04)}
A common vulnerability in naive schemas is allowing an order to select an address belonging to a different customer if both \texttt{customer\_id} and \texttt{delivery\_address\_id} are checked independently. To prevent this at the database level:
\begin{enumerate}
    \item A composite unique constraint is defined on \texttt{customer\_address(address\_id, customer\_id)}.
    \item In \texttt{delivery\_order}, a composite foreign key is established:
\begin{verbatim}
CONSTRAINT fk_order_address
  FOREIGN KEY (delivery_address_id, customer_id)
  REFERENCES customer_address(address_id, customer_id)
  ON DELETE RESTRICT
\end{verbatim}
\end{enumerate}
This completely guarantees that an order cannot be inserted with an address belonging to another customer, enforced directly by the database engine without application code or triggers.

\subsection{Single Default Address per Customer (BR-05)}
Standard \texttt{UNIQUE} constraints on \texttt{is\_default} would incorrectly restrict the entire table to a single default address. Instead, PostgreSQL's partial index feature is utilized:
\begin{verbatim}
CREATE UNIQUE INDEX uq_customer_default_address
  ON customer_address(customer_id)
  WHERE is_default = TRUE;
\end{verbatim}
This index indexes only rows where \texttt{is\_default} is true, permitting any number of non-default addresses per customer while strictly enforcing at most one default address per customer at the database level.

\subsection{Minimum Cardinality of Packages (BR-06)}
Standard foreign keys enforce that a package references an order ($N:1$), but relational DDL cannot natively enforce that every newly inserted order must immediately contain at least one package ($1:1..N$ on the parent side) in a single atomic statement without circular dependencies. In this design, this is documented as a schema constraint requiring transaction-level enforcement (inserting order and package within the same database transaction) or a deferred constraint trigger.

\section{Referential Integrity and Delete Policies}\label{s:referentialval}

The schema establishes clear and consistent deletion policies (\texttt{ON DELETE}) across all foreign keys:

\begin{itemize}
    \item \textbf{Operational Master Data (\texttt{RESTRICT})}: Deleting rows from \texttt{customer}, \texttt{drone}, \texttt{landing\_station}, \texttt{delivery\_order}, or \texttt{delivery\_activity} is blocked if dependent historical or operational child rows exist. This protects the operational record from accidental cascading deletions.
    \item \textbf{Security Bridge Tables (\texttt{CASCADE})}: Deleting a role or permission cascades to \texttt{user\_role} and \texttt{role\_permission}, as the bridge records have no semantic meaning once the parent security entity is removed.
    \item \textbf{User Accountability and Audit References (\texttt{SET NULL})}: When user accounts are archived or purged, operational history and audit records are preserved:
    \begin{itemize}
        \item \texttt{order\_status\_history.changed\_by} $\to$ \texttt{SET NULL}.
        \item \texttt{delivery\_activity.assigned\_by} $\to$ \texttt{SET NULL}.
        \item \texttt{delivery\_exception.resolved\_by} $\to$ \texttt{SET NULL}.
        \item \texttt{audit\_log.user\_id} $\to$ \texttt{SET NULL}.
    \end{itemize}
    This ensures that historical telemetry, exceptions, and audit logs remain intact for compliance even if the originating user record is modified.
\end{itemize}

\section{History Preservation and Audit Architecture}\label{s:historyauditval}

A central design requirement is distinguishing between business state history and security audit trails:

\begin{itemize}
    \item \textbf{Business History (\texttt{order\_status\_history}, \texttt{station\_status\_history})}:
    \begin{itemize}
        \item Answers: \textit{``What was the operational state of this business entity over time?''}
        \item Stores discrete business transitions (\texttt{PENDING $\to$ APPROVED $\to$ ASSIGNED $\to$ IN\_TRANSIT $\to$ DELIVERED}) with transition timestamps and business reasons.
        \item Designed to be append-only at the operational level.
    \end{itemize}
    \item \textbf{Audit Logging (\texttt{audit\_log})}:
    \begin{itemize}
        \item Answers: \textit{``Who modified which record, when, and what changed?''}
        \item Captures low-level DML mutations (\texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}) along with \texttt{JSONB} snapshots of the record before and after modification, client IP address, and actor ID.
        \item Structural separation guarantees that high-volume security logging does not pollute business reporting queries.
    \end{itemize}
\end{itemize}

\section{Normalization Validation}\label{s:normalizationval}

The schema design is formally validated against the rules of relational normalization:

\subsection{First Normal Form (1NF)}
\begin{itemize}
    \item \textbf{Atomicity}: All column domains contain atomic, indivisible values. Address lines, districts, cities, and coordinates are split into dedicated columns in \texttt{customer\_address}.
    \item \textbf{No Repeating Groups}: Package dimensions are stored as distinct scalar numeric attributes (\texttt{length\_cm}, \texttt{width\_cm}, \texttt{height\_cm}) rather than composite text strings (e.g., ``$30\times 20\times 10$''). Multiple addresses or packages are modeled as independent rows.
\end{itemize}

\subsection{Second Normal Form (2NF)}
\begin{itemize}
    \item Every relation is in 1NF.
    \item All non-key attributes are fully functionally dependent on the primary key.
    \item In associative tables with composite keys (\texttt{user\_role} with PK \texttt{(user\_id, role\_id)} and \texttt{role\_permission} with PK \texttt{(role\_id, permission\_id)}), no non-key attribute depends on a proper subset of the composite key. In \texttt{user\_role}, \texttt{assigned\_at} depends on both the user and the role.
\end{itemize}

\subsection{Third Normal Form (3NF)}
\begin{itemize}
    \item Every relation is in 2NF.
    \item No transitive functional dependencies exist ($X \to Y$ and $Y \to Z$ where $Z$ is a non-key attribute).
    \item \texttt{delivery\_order} contains \texttt{customer\_id} as a foreign key; customer name, phone number, and email are not duplicated in \texttt{delivery\_order}.
    \item \texttt{delivery\_confirmation} references \texttt{order\_id} and \texttt{activity\_id}; it does not store drone model or customer contact information.
    \item \texttt{tracking\_record} references \texttt{activity\_id}; drone specifications are accessed through the relation chain \texttt{tracking\_record $\to$ delivery\_activity $\to$ drone} without redundant data duplication.
\end{itemize}

\section{Index and Query Design Validation}\label{s:indexval}

Indexes are designed strictly to support anticipated operational query patterns without imposing unneeded write overhead on high-frequency tables:

\begin{itemize}
    \item \textbf{Foreign Key Lookup Indexes}: Essential for high-frequency relational joins. Indexes on \texttt{delivery\_order(customer\_id)}, \texttt{order\_status\_history(order\_id)}, \texttt{delivery\_activity(order\_id)}, \texttt{delivery\_activity(drone\_id)}, \texttt{station\_operator\_assignment(station\_id)}, and \texttt{package\_station\_event(package\_id)} prevent sequential table scans during join operations.
    \item \textbf{Composite Time-Series Index}: The \texttt{tracking\_record} table receives continuous GPS and telemetry points during flight. The composite index:
\begin{verbatim}
CREATE INDEX idx_tracking_activity_time
  ON tracking_record(activity_id, recorded_at DESC);
\end{verbatim}
    optimizes retrieval of the most recent telemetry coordinates for live monitoring dashboards while scoping scans to a single delivery activity.
    \item \textbf{Implicit Constraint Indexes}: Redundant explicit indexes are avoided on columns already backed by unique b-tree indexes created by \texttt{UNIQUE} constraints (\texttt{system\_user.username}, \texttt{drone.serial\_number}, \texttt{landing\_station.station\_code}, \texttt{delivery\_confirmation.order\_id}).
\end{itemize}

\section{Enforcement Limitations and Boundaries}\label{s:limitationsval}

A sound database design must acknowledge the boundary between what is enforceable directly by declarative SQL schema definitions and what requires procedural or application-level enforcement:

\begin{enumerate}
    \item \textbf{Declarative Schema Enforcement (Directly in PostgreSQL)}:
    \begin{itemize}
        \item Entity integrity (PKs, identities).
        \item Referential integrity (FKs, deletion policies).
        \item Uniqueness (Single default address via partial index, single confirmation per order via unique constraint).
        \item Address ownership (Composite FK linking order and address via customer ID).
        \item Scalar domain checks (positive weights, coordinates, valid status codes).
    \end{itemize}
    \item \textbf{Procedural / Trigger Enforcement (Requires Stored Logic)}:
    \begin{itemize}
        \item \textbf{Cross-record Payload Limit (BR-18)}: Validating that the sum of package weights for an activity does not exceed \texttt{drone.max\_payload\_kg} requires aggregating across multiple package records.
        \item \textbf{Drone Flight Concurrency (BR-16)}: Preventing overlapping flight schedules for the same drone during active status requires a temporal exclusion constraint (\texttt{EXCLUDE USING gist}) or a validation trigger before activity activation.
        \item \textbf{State Transition Lifecycle (BR-12, BR-13, BR-14)}: Preventing invalid status rollbacks (e.g., from \texttt{DELIVERED} back to \texttt{ASSIGNED}) requires a transition validation trigger or application state machine.
        \item \textbf{Active Staffing Authorization (BR-28)}: Confirming that the user recording a package event is actively assigned to that station requires a validation trigger against \texttt{station\_operator\_assignment}.
    \end{itemize}
\end{enumerate}
Documenting these boundaries ensures academic integrity and prevents unsubstantiated claims during project defense.

\section{Chapter Summary}\label{s:ch4summary}

\qquad This chapter conducted a systematic validation of the proposed SmartDroneDelivery database design. All structural aspects—including primary keys, foreign keys, candidate keys, domain check constraints, and referential actions—were verified against the system requirements.

The validation matrix confirmed that all thirty-nine business rules are explicitly represented within the relational model. Advanced relational techniques—such as composite foreign keys for customer address ownership (BR-04) and partial unique indexes for default addresses (BR-05)—were demonstrated. The structural separation between business state history and security audit logging was validated, and 3NF compliance was confirmed.

Finally, the chapter clearly demarcated the boundaries between declarative database constraints and procedural/application-level business logic, providing an honest, rigorous, and defensible foundation for the database design.
