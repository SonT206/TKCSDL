\section{System Overview}\label{s:overview}

\qquad The SmartDroneDelivery platform is an AI-powered Drone Delivery Management Platform designed to support the management of drone-based delivery operations. The system focuses on business and logistics management rather than direct drone control.

The platform supports the complete delivery lifecycle, beginning with the creation of a delivery request and continuing through package management, delivery scheduling, delivery execution, delivery tracking, and delivery confirmation.

From a database perspective, the system requires a structured and reliable data management layer capable of storing and maintaining all information generated throughout these business processes. This chapter identifies the actors, functional requirements, business rules, and data requirements that form the foundation of the database design.

\section{System Actors and Data Responsibilities}\label{s:actors}

The SmartDroneDelivery platform supports five main human actors. Each actor interacts with different functions of the system and is associated with specific categories of data that the database must manage.

\subsection{Customer}

The Customer actor represents individuals who use the platform to request drone delivery services. The database must manage the following data on behalf of this actor:
\begin{itemize}
    \item Customer identification and profile information.
    \item Customer account linked to the system user record.
    \item One or more delivery addresses associated with the customer.
    \item Delivery orders created by the customer.
    \item Delivery confirmation records associated with completed orders.
\end{itemize}

\subsection{Dispatcher}

The Dispatcher actor is a staff member responsible for reviewing and scheduling delivery orders. The database must provide this actor with access to:
\begin{itemize}
    \item Pending delivery orders awaiting review.
    \item Current order status and status history.
    \item Delivery activity records, including drone assignment.
    \item Rescheduling information for failed or cancelled deliveries.
\end{itemize}

\subsection{Station Operator}

The Station Operator actor manages the physical landing stations used in delivery operations. The relevant data includes:
\begin{itemize}
    \item Landing station identification and location information.
    \item Current station status and capacity.
    \item Station status history records.
    \item Station operator assignments linking operators to designated stations.
    \item Package station events, including arrival, pickup confirmation, loading, and unloading.
    \item Delivery activities originating from or terminating at a given station.
\end{itemize}

\subsection{Logistics Manager}

The Logistics Manager actor monitors overall operations and uses data for reporting and analytics. The relevant data includes:
\begin{itemize}
    \item Aggregated delivery order and activity data.
    \item Tracking records for monitoring delivery progress and flight trajectories.
    \item Delivery exception, incident, and failure records.
    \item Station operational metrics and operator assignments.
    \item Data required for operational reports and AI-assisted analytics.
\end{itemize}

\subsection{System Administrator}

The System Administrator actor manages the technical aspects of the system. The relevant data includes:
\begin{itemize}
    \item System user accounts and account status.
    \item Role and permission assignments.
    \item Audit log records for all important system actions.
\end{itemize}

\section{Functional Requirements}\label{s:functional}

This section describes the main functions that the SmartDroneDelivery platform must support from a database perspective. The functional requirements are grouped according to the core modules of the system.

\subsection{User Management}

The user management module handles account registration, authentication, and role-based access control for all system actors.
\begin{enumerate}
    \item The system shall allow customers to register and manage their own accounts.
    \item The system shall allow administrators to create, update, and deactivate accounts for staff members, including dispatchers, station operators, and logistics managers.
    \item The system shall authenticate users through a secure login mechanism using password hashing.
    \item The system shall assign roles and permissions to each account and restrict access to functions according to that role.
    \item The system shall allow users to view and update their personal profile information.
\end{enumerate}
This module requires the database to store account credentials (\texttt{system\_user}), roles (\texttt{role}), permissions (\texttt{permission}), and their bridge assignments (\texttt{user\_role}, \texttt{role\_permission}).

\subsection{Customer and Delivery Order Management}

This module supports the management of customer information and delivery orders.
\begin{enumerate}
    \item The system shall allow customers to manage one or more delivery addresses, including setting a default address and geographic coordinates.
    \item The system shall allow customers to create a delivery request by specifying the delivery address, requested delivery time, and package physical details.
    \item The system shall allow dispatchers to review, approve, or reject submitted delivery requests.
    \item The system shall allow customers and staff to view the current status and full history of their delivery orders.
    \item The system shall allow a delivery order to be modified or cancelled before it is scheduled.
\end{enumerate}
This module requires the database to store customer profiles (\texttt{customer}), delivery addresses (\texttt{customer\_address}), delivery orders (\texttt{delivery\_order}), package details (\texttt{package}), and order status history (\texttt{order\_status\_history}).

\subsection{Delivery Workflow and Execution}

This module supports the scheduling, execution, and confirmation of delivery activities.
\begin{enumerate}
    \item The system shall allow dispatchers to schedule an approved delivery order by creating a delivery activity, selecting pickup and destination stations, and assigning an available operational drone.
    \item The system shall verify that the total package weight does not exceed the assigned drone's payload capacity.
    \item The system shall record package station events, ensuring package pickup and loading are confirmed by an assigned station operator prior to drone departure.
    \item The system shall record real-time flight telemetry and tracking information generated during delivery execution.
    \item The system shall allow confirmation of delivery upon successful handover, capturing receiver details, confirmation method, and a digital evidence key.
    \item The system shall record failed delivery attempts with comprehensive exception reasons and support rescheduling by creating a new linked delivery activity.
\end{enumerate}
This module requires the database to store delivery activities (\texttt{delivery\_activity}), package station events (\texttt{package\_station\_event}), tracking records (\texttt{tracking\_record}), delivery confirmations (\texttt{delivery\_confirmation}), and delivery exceptions (\texttt{delivery\_exception}).

\subsection{Landing Station and Operator Management}

This module supports the management of landing stations and station staffing used during delivery operations.
\begin{enumerate}
    \item The system shall allow station operators to register and update landing station information, including geographic coordinates and capacity.
    \item The system shall record operator assignments to stations, ensuring only assigned operators perform station operations.
    \item The system shall monitor station availability and record all station status changes, such as maintenance or capacity limits, in an immutable history.
\end{enumerate}
This module requires the database to store landing stations (\texttt{landing\_station}), station status history (\texttt{station\_status\_history}), and station operator assignments (\texttt{station\_operator\_assignment}).

\subsection{Dashboard and AI-assisted Services}

This module provides operational monitoring and AI-assisted functions to support logistics managers and dispatchers.
\begin{enumerate}
    \item The system shall provide a dashboard displaying the status of delivery orders, drones, and landing stations.
    \item The system shall store AI-generated recommendations for drone selection, route planning, and estimated time of arrival (ETA).
    \item The system shall provide operational analytics based on historical delivery and tracking data.
\end{enumerate}
This module requires the database to store historical operational data, planned routes (\texttt{delivery\_route}, \texttt{route\_point}), and AI recommendation results (\texttt{ai\_recommendation}). The database does not store AI model weights or code.

\section{Non-functional Requirements}\label{s:nonfunctional}

In addition to functional requirements, the system must satisfy several non-functional requirements that directly affect database design decisions.

\subsection{Security}
The system shall provide secure authentication and role-based authorization. Sensitive credentials must be stored as cryptographic hashes (\texttt{password\_hash}). The database design must enforce access control through relational permissions and prevent unauthorized access to customer and operational records.

\subsection{Performance}
The system is expected to provide a response time of less than three seconds for common operational queries. Selective indexing, optimal data types, and non-redundant schemas must be implemented to support high-throughput telemetry writes and rapid lookup.

\subsection{Concurrency}
The system shall support concurrent users, dispatchers, and automated telemetry ingestion while maintaining strict data consistency. Transactions and constraints must prevent race conditions, such as double-booking a drone for overlapping flights.

\subsection{Integration}
The database serves as the persistent foundation for RESTful APIs and event-driven services. Object storage keys (\texttt{evidence\_object\_key}) are stored to link external object storage (MinIO/S3) without bloating PostgreSQL with binary files.

\subsection{Scalability and Maintainability}
The database design must be modular, adhering to Third Normal Form (3NF), allowing future functional extensions (e.g., maintenance schedules, multi-hop routes) without breaking existing relational schemas.

\subsection{Audit and Traceability}
The system shall maintain comprehensive auditability. An append-only audit log table must capture the actor, action type, entity, changed values, and timestamp for all critical data modifications.

\section{Business Process}\label{s:process}

The complete delivery lifecycle is managed through the following systematic workflow:

\begin{enumerate}
    \item \textbf{Order Placement}: A customer creates a delivery order specifying the target delivery address, requested delivery time, and package specifications. The order is stored with an initial status of \texttt{PENDING}.
    \item \textbf{AI Recommendation}: The AI engine processes the order requirements and records recommendations for drone selection and ETA prediction in \texttt{ai\_recommendation}.
    \item \textbf{Review and Approval}: The dispatcher reviews the order and AI recommendations, updating the order status to \texttt{APPROVED} or \texttt{REJECTED}.
    \item \textbf{Scheduling and Drone Assignment}: The dispatcher schedules the delivery, creating a \texttt{delivery\_activity} that links the order to a specific drone, departure station, and destination station. The order status transitions to \texttt{ASSIGNED}.
    \item \textbf{Station Processing and Package Pickup}: The package arrives at the departure station. An assigned station operator inspects the package, recording a \texttt{package\_station\_event} with status \texttt{PICKUP\_CONFIRMED} and \texttt{LOADED}.
    \item \textbf{Flight Execution and Tracking}: The drone takes off. The activity transitions to \texttt{IN\_TRANSIT}. High-frequency telemetry records (coordinates, altitude, speed, battery) are continuously inserted into \texttt{tracking\_record}.
    \item \textbf{Successful Delivery Confirmation}: Upon safe arrival and recipient handover, the recipient signs or provides verification. A \texttt{delivery\_confirmation} record is created with a reference to the proof object in storage. The order and activity statuses are updated to \texttt{DELIVERED}.
    \item \textbf{Exception and Rescheduling}: If flight anomalies or weather issues occur, a \texttt{delivery\_exception} is recorded, and the activity status is updated to \texttt{FAILED}. The dispatcher can reschedule the delivery, which creates a new \texttt{delivery\_activity} linked to the original failed activity via \texttt{previous\_activity\_id}, preserving complete historical traceability.
\end{enumerate}

\section{Business Rules}\label{s:rules}

To ensure complete structural rigor, thirty-nine formal business rules (BR-01 through BR-39) are established. These rules directly govern entity identification, relationship cardinalities, and database integrity constraints.

\paragraph{Customer and Address Rules.}
\begin{itemize}
    \item \textbf{BR-01}: A customer can have multiple delivery addresses.
    \item \textbf{BR-02}: Each delivery order belongs to exactly one customer.
    \item \textbf{BR-03}: Each delivery order uses exactly one delivery address.
    \item \textbf{BR-04}: The selected delivery address must belong to the customer who owns the order.
    \item \textbf{BR-05}: A customer can have at most one default delivery address.
\end{itemize}

\paragraph{Order and Package Rules.}
\begin{itemize}
    \item \textbf{BR-06}: A delivery order must contain at least one package.
    \item \textbf{BR-07}: A delivery order can contain multiple packages.
    \item \textbf{BR-08}: Package weight and physical dimensions (length, width, height) must be strictly positive numeric values.
    \item \textbf{BR-09}: Package status must follow the defined lifecycle (\texttt{CREATED}, \texttt{AT\_STATION}, \texttt{PICKED\_UP}, \texttt{IN\_TRANSIT}, \texttt{DELIVERED}, \texttt{FAILED}, \texttt{RETURNED}, \texttt{DAMAGED}).
\end{itemize}

\paragraph{Order Status and Lifecycle Rules.}
\begin{itemize}
    \item \textbf{BR-10}: Every delivery order has exactly one current status at any given moment.
    \item \textbf{BR-11}: Every order status change must be preserved in an append-only \texttt{order\_status\_history} table.
    \item \textbf{BR-12}: Only valid status transitions are permitted in the order lifecycle.
    \item \textbf{BR-13}: A cancelled order cannot return to an active state.
    \item \textbf{BR-14}: A delivered order cannot be rescheduled.
\end{itemize}

\paragraph{Drone and Operational Rules.}
\begin{itemize}
    \item \textbf{BR-15}: A drone can execute many delivery activities over time.
    \item \textbf{BR-16}: A drone cannot be assigned to two active delivery activities simultaneously.
    \item \textbf{BR-17}: A drone assigned to an active delivery must be in an operational status (\texttt{AVAILABLE}).
    \item \textbf{BR-18}: The total weight of packages assigned to an activity must not exceed the drone's payload capacity (\texttt{max\_payload\_kg}).
\end{itemize}

\paragraph{Delivery Activity and Rescheduling Rules.}
\begin{itemize}
    \item \textbf{BR-19}: One delivery order may be associated with multiple delivery activities over time.
    \item \textbf{BR-20}: Each delivery activity represents one discrete delivery execution attempt.
    \item \textbf{BR-21}: Failed delivery attempt records, exceptions, and tracking data must be preserved.
    \item \textbf{BR-22}: Rescheduling an order creates a new delivery activity that references the failed activity via \texttt{previous\_activity\_id}.
    \item \textbf{BR-23}: Each delivery activity is associated with exactly one drone.
    \item \textbf{BR-24}: Each delivery activity has its own independent status and operational timestamps.
\end{itemize}

\paragraph{Landing Station and Staffing Rules.}
\begin{itemize}
    \item \textbf{BR-25}: A landing station has a defined non-negative capacity.
    \item \textbf{BR-26}: Station status transitions (e.g., maintenance, offline) must be preserved in \texttt{station\_status\_history}.
    \item \textbf{BR-27}: A station operator can be assigned to one or more landing stations over specified time intervals.
    \item \textbf{BR-28}: Only actively assigned station operators may record station operations and verify package pickups.
\end{itemize}

\paragraph{Package Pickup Rules.}
\begin{itemize}
    \item \textbf{BR-29}: A package can be processed at a departure or destination landing station.
    \item \textbf{BR-30}: Package pickup and handover must be explicitly recorded as station events.
    \item \textbf{BR-31}: Package station event records must record the station, performing operator, event type, and timestamp.
    \item \textbf{BR-32}: A package cannot transition to \texttt{IN\_TRANSIT} without a verified pickup event.
\end{itemize}

\paragraph{Delivery Confirmation Rules.}
\begin{itemize}
    \item \textbf{BR-33}: A delivery order has at most one successful delivery confirmation.
    \item \textbf{BR-34}: A delivery confirmation can only be generated for a successfully delivered order.
    \item \textbf{BR-35}: A confirmation is linked directly to the specific successful delivery activity.
    \item \textbf{BR-36}: Recipient identification, confirmation method, and digital proof reference must be preserved.
\end{itemize}

\paragraph{Audit and Traceability Rules.}
\begin{itemize}
    \item \textbf{BR-37}: All critical system actions must be traceable to the responsible user and timestamp.
    \item \textbf{BR-38}: Audit records must capture actor identity, action type, affected table, record ID, and before/after state.
    \item \textbf{BR-39}: Business state history (\texttt{order\_status\_history}, \texttt{station\_status\_history}) and audit logs (\texttt{audit\_log}) represent separate concerns and must be stored in distinct tables.
\end{itemize}

\section{Data Requirements}\label{s:datareq}

Based on the system requirements and thirty-nine business rules, the database must manage the following major categories of data.

\subsection{User and Authorization Data}
Stores authentication credentials, account statuses, roles, permissions, and many-to-many role/permission assignments (\texttt{system\_user}, \texttt{role}, \texttt{permission}, \texttt{user\_role}, \texttt{role\_permission}).

\subsection{Customer and Address Data}
Stores customer profiles and one or more delivery addresses per customer, including street details, administrative divisions, and geographic coordinates for navigation (\texttt{customer}, \texttt{customer\_address}).

\subsection{Delivery Order and Package Data}
Stores customer delivery orders, requested delivery times, estimated arrivals, completion timestamps, and detailed package dimensions and weights (\texttt{delivery\_order}, \texttt{package}, \texttt{order\_status\_history}).

\subsection{Drone and Station Data}
Stores drone physical specifications, operational statuses, battery levels, landing station coordinates, station capacity, status transition history, and operator assignments (\texttt{drone}, \texttt{landing\_station}, \texttt{station\_status\_history}, \texttt{station\_operator\_assignment}).

\subsection{Delivery Activity and Event Data}
Stores discrete execution attempts, drone assignments, departure/destination stations, previous activity links for rescheduling, and station package handling events (\texttt{delivery\_activity}, \texttt{package\_station\_event}).

\subsection{Tracking and Exception Data}
Stores high-frequency flight telemetry (coordinates, altitude, speed, battery) and records flight incidents, failure categories, and resolutions (\texttt{tracking\_record}, \texttt{delivery\_exception}).

\subsection{Confirmation Data}
Stores formal proof of delivery, recipient name, contact number, confirmation method, and object storage key for digital signatures or photos (\texttt{delivery\_confirmation}).

\subsection{Route and AI Recommendation Data}
Stores planned waypoint paths and AI recommendation outputs including drone selection, duration predictions, and confidence scores (\texttt{delivery\_route}, \texttt{route\_point}, \texttt{ai\_recommendation}).

\subsection{Audit Data}
Preserves an immutable audit trail capturing actor IDs, action types, table names, affected record IDs, JSON before/after snapshots, and IP addresses (\texttt{audit\_log}).

\section{Chapter Summary}\label{s:ch2summary}

\qquad This chapter established the comprehensive database requirements analysis for the SmartDroneDelivery platform. The five system actors and their specific data responsibilities were defined. Functional requirements across five core operational modules and non-functional constraints were specified.

The complete delivery lifecycle was articulated from order placement through package station pickup, drone flight tracking, exception handling, rescheduling, and final confirmation. Thirty-nine formal business rules (BR-01 through BR-39) were defined to eliminate ambiguity. Finally, the traceability matrix demonstrated how all requirements map directly to twenty-three relational entities, establishing a robust foundation for the conceptual, logical, and physical database design in Chapter~\ref{c:design}.
